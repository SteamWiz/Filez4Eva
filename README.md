# Filez4Eva

⚠️ DISCLAIMER: This is a hobby/personal project. Not a commercial product. Not for production use.

## Rename and stow files with structured patterns

The following document is for _developers_ contributing to the application. For information about how to _use_ the application, see [PACKAGE.md](PACKAGE.md).

## Development setup

Requires Python 3.14 or higher. Uses [Dyngle](https://dyngle.steamwiz.io/) for administration (installed separately). Shared Dyngle operations live in the `.conf` submodule ([SteamWiz/Conf](https://github.com/SteamWiz/Conf)), so clone with `--recurse-submodules` or run `git submodule update --init`.

- `dyngle run init` - Create the virtual environment and install poetry
- `dyngle run dependencies` - Install the required packages using poetry
- `dyngle run test` - Run tests and report coverage (same as CI/CD)
- `dyngle run style` - Run style checks
- `dyngle run build` - Create a test build
- `dyngle run sandbox` - Reset the sandbox directories for manual testing

GitHub Actions performs the entire build/test/release cycle using the shared [SteamWiz actions](https://github.com/SteamWiz/actions).

## Intake and sidecars

`filez4eva ingest` moves files into the intake and writes an `X.yml` sidecar next to each one (see [PACKAGE.md](PACKAGE.md#ingesting-files)). The helpers for intake names and sidecars (`intake_dir`, `extensions`, `stamp_name`, `stamp_taken`, `sidecar_path`, `in_intake`, `is_ingested`, `read_sidecar`, `write_sidecar`) are module-level functions in `filez4eva/command/ingest_command.py`, for later stages to reuse. X/X.yml pairing (`is_ingested`, `is_companion`) only counts for files whose parent is the intake (`in_intake`). Stamp check-and-claim (`reserve`) runs under `intake_lock(intake)`, an exclusive `fcntl.flock` on the intake directory, so concurrent `ingest` processes on one machine never share a stamp. `stdin_mapping(app)` in `filez4eva/command/__init__.py` (and `Filez4EvaCommand.stdin_mapping()`) reads a YAML mapping piped on stdin. Tests patch `ingest_command.now` to freeze the clock.

## Commands

There are five commands: `ingest`, `transcribe`, `classify`, `review` and `stow`. `Filez4EvaCommand.default` is `None`, so running `filez4eva` with no command gives WizLib's error for a missing command (`Unknown command None`), and an unknown name gives its `unrecognized arguments` error. Each command sets `summary` (its line in the list of commands that `Filez4EvaApp.initialize` adds to `filez4eva --help`, in the order of `Filez4EvaApp.commands`) and `description` (the text of `filez4eva COMMAND --help`); arguments have `help`. `test/test_app.py` covers the command set and the help.

## Stage commands

The shared logic for the stage commands lives in `filez4eva/stage.py`, for `transcribe`, `classify`, `review` and `stow`. A path means new files only. `resolve_path` turns the path argument into a path, expanded and absolute but not resolved, so messages and output use paths as the user and the configuration give them; a path that is the intake or anything in or under it is refused, checked on the resolved path so a symbolic link or `..` can't get round it. `new_files` lists the new files for a path: a file on its own, or the non-hidden regular files at the top level of a directory. `find_ingested` turns an `--ingested NAME` (a file name in the intake, or a path to it) into an ingested document in the intake, or raises. `load_sidecar`, `stage_result` and `record_result` read and write `results.<stage>` in `X.yml`, refusing to overwrite a sidecar that can't be read. `StageCommand` adds `--only`, `--ingested` and the optional `path` (and appends `selection_help()` to each command's `--help` description); `handle_vals` refuses `--ingested` with a path. Its `run()` calls `select()` (the `--ingested` documents in the order given; the new files for a path; or, with neither, the ingested documents in the intake, noting on stderr each file there without a sidecar and leaving it alone), sets a `Nothing to ...` status and returns if there is nothing to do, then works in phases: `ingest_all` (path runs only), `transcribe_all` (the transcribe batch: every document that needs it, before any later stage; none under `--only` for the later commands; failed documents drop out), then, for commands after transcribe, `cycle` over `order()` (no-path runs: most advanced first, by `progress`, the latest of `STAGES` recorded, then name order), taking each document through the earlier stages in `requires` it lacks and then `act` before the next one (or skipping it with a note under `--only`). Before the later stages, `cycle` calls `check_given` (given data that conflicts with the document fails it, even one that needs nothing else: a `--cabinet` that differs from its `saved_cabinet`, a value that differs from one in `results.given.data`, or any value for a document already classified or reviewed unless its record has the same value) and, when classify is about to run on the document, `give`, which saves `results.given` (`at`, `cabinet`, and `data`, the given values for that cabinet's fields merged with any saved before) before the model is asked: the saved cabinet, else `--cabinet`, else the only cabinet, else `ask_cabinet`, a `Cabinet: ` prompt with tab completion of the names (empty input raises `NotDone('Skipped')` and writes nothing). With the cabinet and every field given (`complete`), `give` also writes `results.review` with `input: true` in the same write and returns True; `cycle` then skips classify and review for the document (counted as `Given`; a classify or review run prints the document's path), and stow stows it. That record stands in for classify and review under `--only` too (`given_complete`, when the cabinet is known without asking). `reached(results, stage)` counts a document with `results.review` as classified, since such a record has no `results.classify`. `saved_cabinet(results)` reads `results.given.cabinet`, falling back for sidecars from before `results.given` to `results.review.cabinet` and then `results.classify.cabinet`. The stage commands after transcribe take the given data, `--cabinet/-c`, `--date/-d` and `--field/-f NAME=VALUE`, and `StageCommand.handle_vals` loads the cabinets (`self.cabinets`) and rejects an unknown `--cabinet` before any file is touched (it imports `load_cabinets` inside the method, as `filez4eva.stow` imports the transcribe command, which imports `stage`). `run()` then calls `read_given` (only on the command being run, never on the earlier ones it builds), which reads the stdin record (`cabinet`, `data`) once, lets flags win, checks and normalizes every value (an unknown cabinet, a malformed `--field`, an invalid date or an empty normalized value raises before any file is touched) and keeps them in `given_data`, with the names from flags in `flagged`. When the run's cabinet is known (given, or the only one) a `--field` name it lacks is an error up front; otherwise `given_for(cabinet)` checks it per document, so it fails that document only. Names only on stdin that a cabinet lacks are ignored. With given data (`--cabinet` included), `run()` doesn't stop early when every document already has the stage, so each one is still checked. Documents that already have `results.<stage>` are counted, per-file errors are reported and the run carries on, and it raises at the end if any failed. `run()` calls `handle_vals()` on each earlier stage command before any file is touched, so their configuration is checked up front. A subclass sets `name`, `stage`, `done` and `requires` (e.g. `ClassifyCommand.requires = (TranscribeCommand,)`) and implements `act(path)`. `act` can raise `NotDone(label)` to leave a document without the stage (counted in the status under the label, e.g. `Skipped`), or `StopRun` to end the run early (the status ends with `Quit`). The run calls each `act` through `perform`, which counts the document under `done`, or under the label `act` set in `self.outcome` (one of the command's `outcomes`, counted in the status after `done`). A label can be a `(label, note)` pair, shown by `status_label` as e.g. `Not transcribed 1 file (text)`.

Progress output goes to stderr (stdout keeps only the result paths). Each stage command sets `doing` (e.g. `'Transcribing'`), and the running command's `announce(doing, path)` sends `stage_line(doing, path)`, `<doing> <name> (<original-name>)` with the original name from `results.ingest`, before `transcribe_all` and `cycle` call a command's `act` (not for documents counted as already done or recorded from complete given data). `announce` skips a line equal to the one sent last, so the `Classifying` line that `ask_cabinet` sends before the `Cabinet: ` prompt isn't repeated. `ReviewCommand` sets `heading = True`: the heading of its display is its stage line, so the run doesn't announce it. `ingest_all` and `IngestCommand` send `Ingesting <path>`, and `StowCommand.act` sends `Stowed to <path>`. `filez4eva/progress.py` has `ai_progress(doing, done)`, a context manager around the blocking Kwark calls (`transcribe` in `transcribe_file`, `extract` in `ask_model`): when `sys.stderr` is a terminal, a `Spinner` draws its first frame, then a daemon thread redraws it in place (`\r\x1b[K`) every `INTERVAL` seconds with the elapsed seconds, and on exit the line is replaced with `<done> in Ns`, or just cleared on any exception (Ctrl-C included). Not a terminal: nothing is drawn. Tests patch `sys.stderr` with a stream whose `isatty()` is true, and `filez4eva.progress.time.monotonic` and `INTERVAL`; `test.plain` strips WizLib's colour codes from captured stderr.

`ReviewCommand` (`requires = (TranscribeCommand, ClassifyCommand)`) is interactive: `act` shows `results.classify` (with the document's `saved_cabinet`, and the values in `results.given.data`, which `proposal` lays over the classified ones and `show` marks `(given)`) and offers confirm/update/redo/skip/preview/delete/quit (skip and delete raise `NotDone`, quit raises `StopRun`). Confirm saves the proposal as `results.review` without prompting (`confirm`: the saved cabinet's fields in pattern order, the date checked with `valid_date` and other values normalized); a missing or unusable value is refused with `Missing: ... Use (u)pdate.` and the menu is asked again. Update uses `Stower.confirm_values` (see below) with the saved cabinet: no cabinet prompt, just that cabinet's fields pre-filled from the proposed values of the same name; empty input (`CommandCancellation`) goes back to the menu. Redo (`redo`) picks the cabinet with `StageCommand.prompt_cabinet(default)` (several cabinets; empty input returns `None` and changes nothing) or the only one, saves it as `results.given` (keeping the given values of the fields the new cabinet has) and drops `results.classify` in one sidecar write, then runs a `ClassifyCommand` built on first use (`classifier`; review also runs inside stow's cycle, so it doesn't rely on `run()`'s earlier commands) and shows the new proposal. Only redo touches `results.given` or `results.classify`. Review tests mock `wizlib.io.ttyin` for the menu keys and `app.ui.get_text` for the prompts.

`StowCommand` (`requires = (TranscribeCommand, ClassifyCommand, ReviewCommand)`) stows each document as soon as it has `results.review`, so in an interactive run every document is stowed straight after it's confirmed or updated. `act` checks `results.review` (`confirmed`), builds a `Stower` with the reviewed cabinet, date and data (so it never prompts) and calls its `stow()`, the move-and-transcript logic (plan, never overwrite, roll back the file if the transcript can't move); it records no learned values, since they were recorded at review. It then writes `results.stow` and moves `X.yml` to `archived_sidecar(path)`, `<intake>/archive/X.yml`, which it checks is free before anything moves. Ingest's `reserve` passes over a name whose sidecar is already archived, so a later document can always be archived. Given data needs nothing of its own in `StowCommand`: complete given data is recorded as `results.review` (with `input: true`) by `StageCommand.give` before `act`, so the scripted single-file stow (`stow -d DATE -f NAME=VALUE FILE`, or a record on stdin) prints just the destination with no model call or prompt. Its tests (`test/test_command_stow_stage.py`) reuse `ReviewTestCase` with `command_class = StowCommand`.

`filez4eva/stow.py` holds the cabinets (`Cabinet`, `load_cabinets`, transcript locations) and `Stower`, the stow logic for one file. `Stower` is a plain class, not a command, so it never shows up as one; it takes the app and the same values a command would (`file`, `cabinet`, `date`, `data`, `field`, `use_stdin`). `read_values` fills in the cabinet and fields from `--field` flags, then stdin (with `use_stdin`), then prompts (the stage commands don't use it: given data is read by `StageCommand.read_given` and never prompted for); `confirm_values` confirms a proposed record for a fixed cabinet at pre-filled prompts; `plan` works out the destinations without moving anything; `stow` moves the file and its transcript (and records no learned values). `remember_values(app, cabinet, data)` records the values of a cabinet's learned fields when `results.review` is saved: by `ReviewCommand.act` after confirm or update, and by `StageCommand.give` when complete given data creates the review (not when the document already had one), so each document counts once. A failure to read or write `values.yaml` is a warning, after the review is saved. Classification (`cabinet_vocabulary`) and tab completion (`Stower.choices`) read the store for every document, so a value that reaches `MIN_COUNT` during a run is offered for the next document. `test/test_stow.py` tests it directly, through `execute` (`read_values` then `stow`) and `start_stower` (the same with an app set up from a configuration file and the stow command's flags).

`ClassifyCommand` never picks the cabinet and never asks the model for one: it checks the doctypes in `handle_vals` (the cabinets and `--cabinet` are checked by `StageCommand`), and `act` classifies for the document's `saved_cabinet` (`classify_text`), which `give` saved before, asking the model only for the fields not in `results.given.data` (`build_schema`, `build_instructions` and `check_result` take the given values; the instructions list them as already given). `results.classify.data` holds every field of the cabinet: the given values and the model's. `results.classify` holds no cabinet. `transcribe_file` in `transcribe_command.py` is the in-place transcription with the sha256 cache, used by `TranscribeCommand.act`; it refuses any type not in `TRANSCRIBABLE` (PDF and images) before calling Kwark. Text documents skip it: `read_text` returns a document's text when its extension isn't in `TRANSCRIBABLE` and its bytes decode as strict UTF-8 with no NUL, and `act` then records `results.transcribe` with `raw: true` (`RAW`), `at` and `length`, writes no `X.md`, and sets `outcome = TEXT_DONE`. Anything else fails with `unsupported(path)`. `is_raw(results)` tells the later stages: `ClassifyCommand` reads the file itself (`document_source`, `read_raw`) instead of `X.md`, `document_text` heads it `Document text:` instead of `Transcript:` and cuts either to `MAX_CLASSIFY_CHARS` with a note in the heading, and `StowCommand` builds its `Stower` with `transcript=False`, so `plan` moves no `X.md`. `write_atomically` lives in `filez4eva/atomic.py`. Stage tests set `FILEZ4EVA_INTAKE` to a temporary directory as well as the config, so no test can touch the real intake.

## Test isolation

`test/conftest.py` keeps results independent of the machine running the tests. For the whole run, temporary files (`tempfile`, so every `TemporaryDirectory`) live behind a symbolic link, as they do on macOS, where `/var` is a link to `/private/var`; a command that mixes resolved and unresolved paths fails on Linux CI too. Each test starts with no `FILEZ4EVA_*` environment variables, an empty `HOME` (no `~/.filez4eva.yml`, no `~/.filez4eva/intake`) and `FILEZ4EVA_CONFIG` pointing at an empty file (so a `.filez4eva.yml` in the working directory is ignored). Tests that need such state set it up in a temporary location. `test/test_environment.py` checks the isolation is in place.

## Libraries

The application uses the following external libraries:

- [WizLib](https://wizlib.steamwiz.io/) for CLI and configuration handling
- [Kwark](https://github.com/SteamWiz/Kwark) (its `kwark.ai` library layer) for transcribing files to Markdown and classifying them with Claude. Filez4Eva passes its own settings (model, API key) as arguments and never reads Kwark's configuration. Tests mock `kwark.ai.transcribe` and `kwark.ai.extract`, so no API calls are made.

Note that this application makes heavy use of WizLib and all code changes are expected to comply with, and take advantage of, the framework.
